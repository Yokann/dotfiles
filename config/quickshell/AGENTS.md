# Design notes

Quickshell 0.3 bar for Hyprland. Read this before adding or changing anything.

**Never judge a visual result (spacing, colors, layout, whether a popup rendered/looks right, etc.) by taking a screenshot yourself and eyeballing it.** After making a visual change, describe what changed and ask the user to check it live instead of self-verifying with grim/screenshots.

## Layout

```
shell.qml            ShellRoot, imports modules/bar
settings.json         user config, committed with sane defaults
config/
  Settings.qml         Singleton: FileView + JsonAdapter over settings.json
theme/
  Colors.qml             Singleton: Catppuccin Macchiato palette
  Metrics.qml             Singleton: shared spacing/radius/font sizes
ui/
  BarWidget.qml              widget-contract base (instanceId/screen/panelWindow + resolveStyle)
  WidgetButton.qml            multi-button/scroll clickable chrome, composed inside a BarWidget
  Popup.qml                 reusable popup chrome (background, scrolls if content overflows)
  Slider.qml                 draggable 0-1 value bar (value + moved(value))
  Dropdown.qml                 collapsible option list (options + currentLabel + selected(value))
widgets/
  Registry.qml             Singleton: static id -> Component map
  <name>/                   one self-contained widget per directory
modules/
  bar/Bar.qml               One bar, parameterized by a bar config; Variants over
                             Quickshell.screens, one PanelWindow per screen
services/
  Audio.qml                  Singleton wrapping Quickshell.Services.Pipewire (sink/source
                              volume, mute, device lists, PwObjectTracker binding)
  <Name>.qml                Singleton wrapping a system integration (added as needed per widget)
```

`shell.qml` instantiates one `Bar { barConfig: ... }` per entry of `Settings.bars` (`Variants { model: Settings.bars }`) — this is what makes multiple bars possible, see Settings below.

All internal imports use `import qs.<path>` (resolved relative to `shell.qml` by Quickshell itself — no manual `qmldir`).

## Settings

`settings.json` has a `bars` array (each entry: identity, geometry, and per-screen layout) and a `widgets` dictionary keyed by **instance id** for widget-specific settings:

```json
{
  "bars": [
    {
      "id": "main",
      "position": "top",
      "height": 34,
      "layout": {
        "default": { "left": ["clock_date", "clock_time"] },
        "HDMI-1": { "left": ["clock_time", "pomodoro"] }
      }
    },
    {
      "id": "secondary",
      "position": "bottom",
      "height": 34,
      "layout": { "default": { "left": ["tray"] } }
    }
  ],
  "widgets": {
    "clock_time": { "type": "clock", "format": "HH:mm" },
    "clock_date": { "type": "clock", "format": "dddd d MMMM" }
  }
}
```

Each `bars[]` entry becomes one independent bar, rendered on every screen (`shell.qml`: `Variants { model: Settings.bars }` instantiating `Bar { barConfig: ... }`) — `id` just needs to be unique per entry, it isn't otherwise interpreted. `Settings.bars` is computed by merging each raw entry over `{ id: "main", position: "top", height: 34, background: "base", layout: {} }` in `Settings.qml`, so a `bars[]` entry can omit any field it doesn't need to override. (A `list<JsonObject>`-typed adapter property doesn't deserialize a JSON array of objects correctly in this Quickshell version — `bars` is `property var` on the `JsonAdapter`, with defaults applied in QML instead of via a typed sub-object like the rest of this doc's `defaults` pattern.)

`background` is resolved through `Colors.resolve(barConfig.background)` (`Bar.qml`'s `PanelWindow.color`) — same token-or-literal-hex rule as widget `style` colors (e.g. `"base"` or `"#181926"`).

`bar.layout` (one bar's layout, i.e. one entry of `Settings.bars`) maps a screen name (as reported by Hyprland/Quickshell, e.g. `HDMI-1`, `DP-1`) to a set of sections (`left`, `center`, `right`), each an ordered array of **instance ids** — array order is display order, there's no separate `order` field. `default` is the layout used for any screen without its own entry. **A screen's own entry only overrides the sections it defines**: it falls back to `default` section-by-section, so e.g. defining `left` for `HDMI-1` still inherits `default`'s `center` if `HDMI-1` doesn't define one. A widget not listed in any section for a screen simply isn't shown there — there's no separate `enabled` flag.

### Instance ids vs widget types

A layout section never names a widget type directly — it names an **instance id**. An instance id is resolved to a widget type (a key in `widgets/Registry.qml`) via `widgets.<instanceId>.type`; if that's absent, the instance id doubles as the type id. This is what lets `clock_time` and `clock_date` both be `type: "clock"` with a different `format`, i.e. the same widget declared twice with different config — for a widget you only need once, skip `widgets` entirely and put the type id straight into the layout (e.g. plain `"clock"`).

`Settings.widgetType(instanceId)` resolves the type; `Settings.widgetConfig(instanceId, defaults)` merges that instance's config (minus `type`) over the type's defaults. `widgets` and `bar.layout` are both `property var`, not typed objects — **`Settings.qml` never needs to change when a widget is added**, which is what keeps the architecture plugin-friendly.

## Widget contract

A widget is a directory under `widgets/<name>/` with at minimum a `<Name>.qml` bar component (and a `<Name>Popup.qml` if it has one). To register it:

1. Add one line to `widgets/Registry.qml` mapping its type id to its `Component` and default config.
2. Reference that type id (or an instance id declared under `widgets` with a matching `type`) from a section in one of `settings.json`'s `bars[].layout` to actually show it.

No other file changes. Widget registration is a static declarative map, not a runtime dynamic loader — simpler and safer in QML than resolving component paths from strings at runtime.

`Bar.qml` reads `Settings.sectionWidgets(barConfig, sectionId, screenName)` for each of the three sections; for each instance id it resolves the type via `Settings.widgetType`, instantiates `Registry.definitions[type].component`, and sets `instanceId`, `screen`, **and `panelWindow`** on the loaded item — **every widget must expose settable `instanceId` (string), `screen` (the `ShellScreen` it's rendered on), and `panelWindow` (the `PanelWindow` it's rendered in) properties** (all three inherited for free by anything built on `ui/BarWidget.qml`) so it can look up its own config with `Settings.widgetConfig(instanceId, defaults)`, scope itself to its screen if relevant (e.g. Workspaces uses `Hyprland.monitorFor(screen)`), or open a native platform menu (needs an actual window, not just any QML `Item` — see Tray below). A widget that doesn't extend `BarWidget` must declare all three itself (see `widgets/workspaces/Workspaces.qml`, `widgets/tray/Tray.qml`).

## UI building blocks (`ui/`)

`ui/` holds generic, widget-agnostic pieces of chrome — not widgets themselves, nothing in there is registered or configured directly. `BarWidget.qml`, `WidgetButton.qml`, `Popup.qml`, `Slider.qml`, and `Dropdown.qml` live here because they're meant to be reused by any future widget. **Default to putting a new atomic design element here** (a slider, a toggle, a dropdown, ...) rather than inlining it in a widget file, even the first time it's needed — `Slider`/`Dropdown` moved here directly out of the Audio popup rather than waiting for a third use, since they're obviously general-purpose. Only leave something local to a widget if it's genuinely specific to that widget's domain (e.g. `Workspaces.qml`'s per-cell styling, which encodes Hyprland-specific active/focused/occupied states, not a generic list item).

**Composition, not inheritance**: a widget extends `BarWidget` for the instanceId/screen/panelWindow contract (plus a `resolveStyle(defaults)` helper), and composes one or more `WidgetButton`s as children for the actual clickable chrome — e.g. `BarWidget { WidgetButton { onClicked: ...; onRightClicked: ...; Text { ... } } }`. `WidgetButton` itself takes a plain `styleOverrides` object (not an `instanceId`) so it stays fully generic and reusable more than once inside a single widget — this is what lets a future container with several independently-clickable cells use one `BarWidget` root with several `WidgetButton` cells inside it, instead of forcing the whole container to be one clickable item. `WidgetButton` handles all three mouse buttons (`clicked()`/`middleClicked()`/`rightClicked()`), wheel scrolling (`scrolled(delta)`, from `wheel.angleDelta.y`), and two independent state flags (`idle`, `inactive`) that layer their own background/text-color pair on top of the normal hover/normal colors, for widgets that need more than a plain hover recolor. Every bar item in the tree is now built this way (`Clock`, `AudioIndicator`, `UpdatesIndicator`, `SysmonitorIndicator`, `PomodoroIndicator`, `IdleInhibitorIndicator`, `Button`, `NotificationsIndicator`) — see "Decisions from scoping" below for how this superseded the original `ui/Pill.qml` (single-left-click-only chrome most of these widgets used to extend, deleted once nothing referenced it anymore) and the hand-rolled `Rectangle`+`MouseArea` `Button.qml`/`NotificationsIndicator.qml` used before.

`widgets/workspaces/Workspaces.qml` still doesn't fit this shape today: it needs a background *container* around several independently-clickable items, and currently has its own root `Rectangle` duplicating a small style-resolution snippet (`Settings.widgetStyle(instanceId, { background, radius })` → `Colors.resolve`) rather than using `BarWidget`/`WidgetButton` — migrating it (one `BarWidget` + one `WidgetButton` per workspace cell) is a natural next step the composition model was specifically designed to support, just not done yet. `widgets/tray/Tray.qml` also stays as its own `Rectangle`+`MouseArea` shape, since a tray item's `display()` context menu needs `panelWindow` and click-coordinate mapping that doesn't fit `WidgetButton`'s signal shape as cleanly.

Ask if a design change should affect everything, if so, affect change in the UI class instead repeating change in every widget.

## Widget styling

`ui/WidgetButton.qml` resolves its look from `widgets.<instanceId>.style`, through composition rather than direct `instanceId` resolution: the widget composing it (a `BarWidget`) calls `resolveStyle(defaults)` (inherited from `ui/BarWidget.qml`, wrapping `Settings.widgetStyle`) and passes the result in as `WidgetButton.styleOverrides`:

```json
"widgets": {
  "clock_time": {
    "type": "clock",
    "style": { "background": "surface1", "hoverBackground": "accent", "radius": 8, "hoverDurationMs": 200 }
  }
}
```

A partial `styleOverrides` object is fine — `WidgetButton` merges it over its own internal `defaultStyle` (`style: Object.assign({}, defaultStyle, styleOverrides)`) rather than replacing it outright, so both internal bindings and the composing widget always read the fully-populated `style`, never `styleOverrides` directly (see Memory below for the bug this avoids). `background`/`hoverBackground`/`idleBackground`/`inactiveBackground`/`textColor`/`hoverTextColor`/`idleTextColor`/`inactiveTextColor` each accept either a `Colors` palette key (`"surface0"`, `"accent"`, ...) or a literal color string (`"#ff0000"`) — resolved by `Colors.resolve(token)`. `radius` and `hoverDurationMs` (the hover color transition) are plain numbers. `fontWeight` is a plain number too (Qt6's `font.weight` takes an int 1-1000 directly — `100`≈Thin, `400`=Normal, `700`=Bold, `900`=Black — no string/enum mapping needed).

`WidgetButton` only resolves `style` — it doesn't own the `Text` elements inside it (those are each widget's own `content`, via `WidgetButton`'s default-property alias), so **every widget built on it must itself bind its `Text`'s `font.weight: button.style.fontWeight`** (and similarly would need to for any future font-related key) for the setting to actually apply; adding a key to `WidgetButton`'s style defaults makes it *available*, not automatically wired everywhere. Every current widget (`Clock`, `AudioIndicator`, `UpdatesIndicator`, `SysmonitorIndicator`, `PomodoroIndicator`, `IdleInhibitorIndicator`, `Button`, `NotificationsIndicator`) does this.

`WidgetButton` also exposes `clickable: bool` (default `true`), `idle: bool`, and `inactive: bool` (both default `false`) — set by the composing widget from its own domain setting, not from `style`, since "is this interactive"/"is this idle"/"is this inactive" is widget-specific (e.g. Clock's `showCalendar` drives `clickable`, `UpdatesIndicator`'s "no pending updates" drives `idle`). When `clickable` is `false`, the background goes fully transparent, hover/cursor are disabled, and clicks don't register: the widget reads as plain text, not a button. A widget with an optional popup should also bind the popup's `LazyLoader.loading` to the same condition, so a disabled popup is never even built. `idle`/`inactive` each layer their own background/text-color pair (`idleBackground`/`idleTextColor`, `inactiveBackground`/`inactiveTextColor`) on top of the normal hover/normal colors — `inactiveBackground` defaults to `Colors.inactiveSurfaceBackground` (transparent); `idleBackground`/`idleTextColor` default to the normal `background`/`textColor` (no visual change until a widget's style or its own further override supplies one), since there's no existing "idle" color precedent to default to. `WidgetButton` exposes `resolvedBackground`/`resolvedTextColor` (the fully-resolved current color, accounting for `clickable`/`idle`/`inactive`/`hovered`) so a composing widget can reuse the same expression when layering yet another state on top (see `IdleInhibitorIndicator`'s "committed" lavender override) rather than re-deriving the precedence chain.

This covers color/hover/radius/idle/inactive today; extending it to more style knobs (e.g. font) means adding a key to `WidgetButton`'s `defaultStyle`, not a new mechanism.

## Memory

- Popups always sit behind a `LazyLoader` — nothing builds until the widget is first clicked. **Remember to set `loading: true` on the `LazyLoader`** — without it, `item` stays `null` forever since nothing ever triggers the load (this bit us on the clock's calendar popup). For a lightweight popup (a few dozen items, e.g. the calendar grid), it's fine to just toggle `popupLoader.item.visible` afterwards and leave it resident — this is Quickshell's own documented pattern. Only tear down on close (bind `LazyLoader.active` to visibility instead) for a popup with genuinely heavy content (e.g. a long list rebuilt from a process output).
- On a `PopupWindow`-derived type, set `implicitWidth`/`implicitHeight`, not `width`/`height` — the latter is deprecated and logs a warning.
- Give every `ui/Popup.qml`-based popup a **fixed** `implicitWidth`/`implicitHeight` (like `CalendarPopup`'s `260`/`260`), not one derived from its content's changing implicit size. `AudioPopup.qml` originally used `content.implicitHeight` (plus `ui/Popup.qml`'s `Metrics.spacingMedium` margin, easy to forget and get a squashed bottom padding from) so it would grow/shrink as a `Dropdown` expanded — resizing an already-visible `PopupWindow` visibly flickers (Wayland popup surfaces don't resize cleanly once mapped). Pick a fixed size, not necessarily generous — content taller than that fixed size now just scrolls (see below) rather than needing the window itself to grow.
- `ui/Popup.qml`'s content area is a `Flickable`, with a thin non-interactive scrollbar thumb driven by `Flickable.visibleArea`, so content taller than the popup's fixed height scrolls instead of being clipped. This needs one line of wiring per popup that can actually overflow: set `scrollContentHeight: <yourRootItem>.implicitHeight` on the `Popup` instance (defaults to `0`, meaning "never scrolls" — fine for `CalendarPopup`, which always fits). Three things that look reasonable here but silently break scrolling, all hit while building this:
  - **Don't** compute the Flickable's `contentHeight` from its own `childrenRect.height` — it's measured in scroll-transformed coordinates, so it changes as `contentY` changes, which is itself clamped by `contentHeight`: a binding loop (QML warns "Binding loop detected for property contentHeight"). Use an explicit `scrollContentHeight` fed by the caller instead.
  - **Don't** alias the popup's `content` default property straight into the `Flickable`'s own `data` property. The scrollbar then tracks `contentY` correctly but the actual content never visually moves. `Flickable` needs exactly one plain, directly-nested child to reliably apply its scroll transform — so `content` is aliased into a wrapper `Item` (`contentWrapper`, sized to `flickable.width`/`flickable.contentHeight`) that is itself Flickable's one real child, not into the Flickable directly.
  - **Don't** assume `Flickable`'s built-in wheel handling reaches content inside a Quickshell `PopupWindow` — it didn't in testing. `ui/Popup.qml` has an explicit `MouseArea` (`acceptedButtons: Qt.NoButton`, so clicks still pass through) whose `onWheel` drives `contentY` directly instead.
- Polling services (updates, sysmonitor) use a `refCount` property incremented/decremented by whichever widget instances are alive; their `Timer` only runs while `refCount > 0`. Do not add a free-running `Timer` to a service.
- Audio, tray, and Hyprland workspaces are push-based (Pipewire, SystemTray, `Quickshell.Hyprland`'s own event-socket listener) — no polling `Process`/`Timer` needed for those.
- A widget not referenced by any section for a screen is not instantiated there at all, not just hidden with `visible: false`.
- Instance pragmas (`//@ pragma ...` at the top of `shell.qml`, e.g. `UseQApplication`) only take effect on a full `quickshell` restart, never on hot reload — say so explicitly if a change needs one, don't just wait for the reload to "fix" it.
- Running an external command from a service: `Quickshell.Io.Process` (`import Quickshell.Io`, plus plain `import QtQuick` for `Timer` — easy to drop since most services here are push-based and don't otherwise need it) with `stdout: StdioCollector { onStreamFinished: ... }`, reading `text` once the stream closes rather than accumulating partial reads. Don't gate parsing on the process's exit code — `yay -Qu`/`pacman -Qu`-style tools exit non-zero for "nothing to report", which is not an error.
- When a `sh -c "..."` command needs a section delimiter to split multi-command output (e.g. one `Process` gathering CPU+mem+disk in a single call), don't use `#`/`###` — an unquoted `#` starts a shell comment, silently swallowing the rest of the line (everything after it, including subsequent `;`-separated commands, vanishes: `sh -c "echo A; echo ###; echo B"` prints only `A`). Hit this building `services/Sysmonitor.qml`; use a plain word like `SPLIT` instead.
- A service singleton and the widget that displays it want the same domain name (`Updates`) but a QML type name is its filename, so both can't be `Updates.qml`. Follow the precedent already set by `services/Audio.qml` + `widgets/audio/AudioIndicator.qml`: the widget file gets an `...Indicator` suffix, the service keeps the bare domain name.
- Step 9 polish pass (removed the now-unused `widgets/placeholder/`, audited colors/spacing/hover for stray hardcoded values, checked memory: ~420MB RSS flat over several minutes, no lingering child processes from `Process` calls) found nothing to fix.
- A fire-and-forget `Process` (run a user command, don't care about its output) needs no `stdout`/`StdioCollector` at all — just set `command` and `running: true`. `widgets/button/Button.qml` keeps one such `Process` per mouse button (left/middle/right) rather than sharing one, so e.g. a left-click command still running doesn't block a right-click one from starting (setting `running: true` while already `true` is a no-op, not a queue).
- This QML engine's typed-parameter support (`function f(x: SomeType): ReturnType`, used throughout for e.g. `PwNode`/`string`/`void`) does **not** extend to default parameter values on a typed param (`function f(x: real = 1)`) — errors "Type annotations are not supported (yet)" at the `=`. Give the parameter type `var` and default it manually inside the body instead (`x ?? 1`) if this comes up again.
- Before hardcoding a Nerd Font icon codepoint (like `SysmonitorIndicator.qml`/`PomodoroIndicator.qml` do), check it actually has a real glyph rather than just trusting fontconfig's charset claim: `fc-match -a ":charset=<hex-codepoint-no-0x>"` lists every font fontconfig *thinks* covers it, but some Nerd Font builds declare covering a whole PUA block without every slot in it having an actual glyph drawn — this happened with the idle-inhibitor widget's "disabled" icon (U+F0DDB, "covered" per `fc-match` by the same fonts as every other working glyph in the bar, yet renders blank live). The only real test is rendering it — `fc-match` narrows down font names, it doesn't confirm the glyph exists. Also don't conclude a glyph is broken from a single screenshot right after a hot reload — a stale frame briefly showed the *other* (working, U+F0F4) icon on this same widget as blank too before a second reload/screenshot cleared it.

## Decisions from scoping

- **Theme**: Catppuccin Macchiato, matching the current Hyprland theme (`config/hypr/themes/2024/macchiato.conf`).
- **Updates**: single `yay -Qu` call (covers repo + AUR); no separate `checkupdates` call. `services/Updates.qml` runs it via `Process`/`StdioCollector` on a `refCount`-gated 15-minute `Timer`, plus a manual `poll()` callable from the popup's refresh control. Each output line (`name oldVersion -> newVersion`, with an optional trailing `[age]` suffix some AUR helpers append) is split on whitespace, taking indices 0/1/3 — the bracketed suffix, if present, is simply never read. `UpdatesIndicator.qml` shows `✓` (up to date), `↑N` in `Colors.yellow` (N pending), or `…` while a check is in flight; `UpdatesPopup.qml` lists pending packages with old → new version.
- **Calendar**: month-view popup only, no external agenda/ICS integration.
- **Pomodoro**: in-memory state only, no disk persistence across Quickshell restarts. Classic durations hardcoded in `services/Pomodoro.qml` (25 min work / 5 min short break / 15 min long break, long break every 4th completed work session) rather than made per-widget configurable — this is shared session state, not a per-instance display setting, so it lives on the service like Audio's state does, not behind `Settings.widgetConfig`. Its `Timer` is gated only by `running` (user-controlled via play/pause), not a `refCount` — unlike the updates/sysmonitor polling services, the countdown is meant to keep progressing in the background even if no bar currently renders the widget; only actual sampling work (a `Process` call) is worth skipping when nobody's looking, a plain 1-second in-memory tick is not.
- **System monitor**: CPU (delta of two `/proc/stat` samples 2s apart — a single reading is meaningless since the counters are cumulative since boot), memory (`MemAvailable`/`MemTotal` from `/proc/meminfo`, not `MemFree` — `MemFree` alone overcounts usage since it excludes reclaimable cache/buffers), disk (`df` on `/` only, no per-mount breakdown). All three gathered in one `sh -c` `Process` call per poll rather than three separate processes, to match the "mindful of memory usage" constraint from scoping.
- **Multi-screen**: each bar renders on every screen; per-screen `bar.layout` placement controls which widgets actually show where (see Settings above).
- **Multi-bar**: `settings.json`'s `bars` is a list — any number of independent bars (own id, position, height, layout) can coexist, e.g. a top status bar and a bottom dock-like bar.
- **Audio**: output + input (mic) + sink/source device picker, via `Quickshell.Services.Pipewire`. A `PwNode`'s `audio` property (volume/muted) is only usable once the node is bound by a `PwObjectTracker` — `services/Audio.qml` binds every audio node (`Pipewire.nodes.values.filter(n => n.audio)`), not just the current default sink/source, so the device-picker lists have working state too. Device switching is `Pipewire.preferredDefaultAudioSink/Source = node` (a settable hint, unlike the readonly `defaultAudioSink/Source`) — there's no `node.setAsDefault()`-style method. `PwNode.isStream` distinguishes a real device from an application's individual playback/capture stream; the device lists filter it out. Compare nodes by `node.id` (the PipeWire object id), not object identity, to find the current device in a list — same caution as the workspace-focus fix. Both the output and input device pickers in `AudioPopup.qml` use `ui/Dropdown.qml` (collapsed by default, current device as the header label).
- **Workspaces**: dynamic, not a fixed count — only workspaces that exist in `Hyprland.workspaces` are shown, scoped per-screen via `Hyprland.monitorFor(screen)`. Default Hyprland behavior destroys empty non-active workspaces (no `persistent` rule found in `config/hypr/`), so this already reflects "workspaces actually in use" rather than needing a separate persistence setting. No `services/Hyprland.qml` wrapper — `Quickshell.Hyprland`'s `Hyprland` singleton is already fully reactive with nothing to derive, a wrapper would add nothing.
- **Workspace focus indicator**: use `Hyprland.focusedWorkspace?.id === workspace.id`, not `workspace.focused` — the latter didn't update on a monitor-focus change in testing (only `activeworkspace`/keyboard-focus events reliably retarget `Hyprland.focusedWorkspace`; per-monitor `focused` can lag, matching the docs' note that some monitor-state changes don't emit an event at all). Each workspace cell in `Workspaces.qml` is its own fixed-size `Rectangle` (not just a `Text`) so the whole cell is clickable, not only the glyph — do this for any future multi-item widget, don't rely on a `Text`'s tight bounding box as a click target.
- **Tray**: `Quickshell.Services.SystemTray`'s `SystemTray.items` is global, not per-monitor (unlike workspaces) — `Tray.qml` shows the same icons on every bar/screen that includes it, no `Hyprland.monitorFor` filtering. Icons use `Quickshell.Widgets.IconImage`, not a plain `Image` — it resolves theme icon names, but a tray icon string can also come as `"<name>?path=<dir>"` (some tray implementations serve an icon from an arbitrary directory rather than the icon theme), which needs rewriting to a `file://` URL by hand — see `Tray.qml`'s `source` binding. A tray app can also hand out a broken/missing icon name (seen with `wayscriber-symbolic`, which doesn't exist in any installed theme). Diagnosed via `busctl --user get-property org.kde.StatusNotifierItem-<pid>-1 /StatusNotifierItem org.kde.StatusNotifierItem IconName|IconThemePath|IconPixmap`: `wayscriber` ships no icon file at all, only a raw `IconPixmap` (RGBA bytes over D-Bus) — the SNI-spec fallback for apps that skip installing an icon, which is why waybar (which reads `IconPixmap` itself) shows it fine. `Quickshell.Services.SystemTray`'s `SystemTrayItem` doesn't expose `IconPixmap` at all in its QML API — there's nothing to read even if we wanted to render it, this is a Quickshell limitation, not fixable from widget code without talking to D-Bus directly (judged not worth it for one app). Instead, `Tray.qml` shows a one-letter text fallback (first letter of the item's title/id) whenever `IconImage.status === Image.Error`, so a broken icon reads as a labeled placeholder instead of a blank gap.
- **Tray icons vanishing (blank square, not the letter fallback)**: `SystemTrayItem.icon` can go transiently empty even for an app with a perfectly normal icon — confirmed via quickshell's own log (`/run/user/$UID/quickshell/by-id/<id>/log.log`) showing repeated `quickshell.dbus.properties: Error updating property org.freedesktop.StatusNotifierItem-<pid>-1/.../IconName` / `QDBusError(..., "error occurred in Get")` for Signal Desktop's tray item, unrelated to any quickshell reload (happens on its own schedule, presumably whenever Electron's main thread is briefly too busy to answer the D-Bus property read). When `icon` is `""`, `IconImage.source` is `""`, which leaves `status` at `Image.Null` — not `Image.Error` — so the old `visible: icon.status === Image.Error` fallback check missed this case entirely: neither the icon nor the letter rendered, i.e. the icon just disappeared. Fixed by computing the resolved icon URL into a named `trayItem.iconSource` property once, and keying both `IconImage.visible` and the fallback `Text.visible` off `iconSource === ""` in addition to the `Error` status, so an empty icon always falls back to the letter instead of going blank.
- **Tray context menu (`display()`)**: needs two things that were missing initially. (1) `//@ pragma UseQApplication` at the top of `shell.qml` — native platform menus need Qt's `QApplication`, not the default `QGuiApplication`; this is an *instance* pragma, it only takes effect after a full `quickshell` restart, not a hot reload. (2) The item's own `Item.Window.window` attached property isn't a valid parent for `display()` (errors "must be called with a window") — use the injected `panelWindow` contract property instead, and map click coordinates to window space with `item.mapToItem(null, mouse.x, mouse.y)` since `display(parentWindow, x, y)` wants window-relative coordinates, not coordinates relative to the clicked icon. Left click → `activate()`, middle click → `secondaryActivate()`, right click → `item.display(root.panelWindow, pos.x, pos.y)` when `item.hasMenu`. Since switching to `QApplication`, a `QObject: Cannot create children for a parent that is in a different thread` warning shows up on every startup (from async `IconImage` loading crossing into the `QApplication` thread) — observed harmless so far, revisit if it ever causes an actual crash rather than just a log line.
- **Idle inhibitor**: `Quickshell.Wayland`'s `IdleInhibitor` (from the `Quickshell.Wayland._IdleInhibitor` submodule, but re-exported by the parent `Quickshell.Wayland` module so a plain `import Quickshell.Wayland` is enough) is a plain `QObject`, not a `PopupWindow`/visual item — just `enabled: bool` and `window: QObject*`. `window` takes the injected `panelWindow` contract property directly (a `PanelWindow` is an accepted `QObject*`, no coercion needed, unlike Tray's `display()` case). No service needed — it's simple enough to live entirely in the widget, same reasoning as `Workspaces.qml`. Toggling was verified to engage/disengage cleanly (no runtime errors from the Wayland object itself either way) independently of the icon-glyph problem noted in Memory above. When `inhibiting` is true, the widget overrides the composed `WidgetButton`'s background to `Colors.lavender` and its own `Text`'s color to `Colors.crust`, ignoring the normal hover color while active — a toggled-"on" state reads as committed, not hover-previewable. (Originally built on `ui/Pill.qml`, which needed a `readonly property alias hovered: mouseArea.containsMouse` addition for exactly this — a derived instance overriding `color` had no other way to stay hover-reactive on its non-active branch. Since migrated onto `ui/BarWidget.qml` + `ui/WidgetButton.qml`, which expose the equivalent `resolvedBackground`/`resolvedTextColor` directly — see "Widget styling" above.)
- **Notifications**: `swaync-client -swb` is fundamentally different from every other `Process` call in this project — it's a long-running subscription that prints one JSON line (`{"text": "<count>", "alt": "notification"|"dnd-notification"|..., "tooltip": "...", "class": "..."}`) per state change and never exits on its own, not a one-shot command whose full output you read after it finishes. `services/Notifications.qml` reflects that: `stdout: SplitParser { splitMarker: "\n"; onRead: data => ... }` (not `StdioCollector`/`onStreamFinished`, which waits for the stream to *close*), `running: true` set once at startup rather than via a `poll()`/`refCount` `Timer`, and an `onExited: restartTimer.restart()` to respawn it if swaync itself restarts the subscriber out from under us. DND state is read as `alt.startsWith("dnd")` rather than matching an exact string, since the confirmed values are `"dnd-notification"` (has notifications) and presumably `"dnd-none"` (none) by the same naming pattern — only the former was actually observed live.
- **Tray icon vertical alignment**: `Tray.qml`'s item squares were sized as `Metrics.fontSize + Metrics.spacingMedium`, but `fontSize` (a raw `font.pixelSize`) undershoots a real rendered `Text`'s implicit height (ascent+descent+leading), which is what a `WidgetButton`'s `implicitHeight` is actually built from (`contentRow.implicitHeight + Metrics.spacingSmall * 2`; originally `ui/Pill.qml`'s formula, before that widget shape was migrated onto `WidgetButton` — see below). The mismatch (tray squares a few px shorter) made tray icons look top-aligned instead of vertically centered next to sibling widgets sharing the same bar-section `Row` (a plain `Row` top-aligns children of differing height — it doesn't center them, and anchors can't be added to a `Row`'s direct children to fix it there either). Fixed by measuring an actual hidden reference `Text` (same `font.family`/`pixelSize` as everywhere else) and using `heightReference.implicitHeight + Metrics.spacingSmall * 2` for the square size, matching that formula exactly instead of approximating it from `fontSize` alone. If a similarly-sized container widget is added later (`Workspaces.qml` already computes its own height independently and comes out taller, ~29px vs `WidgetButton`'s ~24-26px, though that's a different bar section so it isn't visibly mismatched today), reach for this same "measure it, don't approximate from `fontSize`" pattern rather than guessing a constant.
- **`ui/BarWidget.qml` + `ui/WidgetButton.qml`**: added to stop the click-handling/style-resolution duplication between `ui/Pill.qml`, `Button.qml`, `NotificationsIndicator.qml`, and `Workspaces.qml`'s "styleable container, independently-clickable children" shape from being re-duplicated a fourth and fifth time — the rule-of-three called out in "UI building blocks" above. Composition was chosen over inheritance (`WidgetButton` does not extend `BarWidget`, it's composed as a child) specifically so a future multi-cell container can reuse `WidgetButton` once per cell instead of the whole container having to become one clickable item, and so `WidgetButton` stays decoupled from `Settings`/`instanceId` (it takes a plain `styleOverrides` object) like the other generic `ui/` chrome. Introduced additively (`Button.qml` refactored onto them first, see Memory below for a gotcha this surfaced), then every remaining `Pill`-based widget (`Clock`, `AudioIndicator`, `UpdatesIndicator`, `SysmonitorIndicator`, `PomodoroIndicator`, `IdleInhibitorIndicator`) and `NotificationsIndicator.qml` were migrated in the same pass — at which point `ui/Pill.qml` had zero remaining references and was deleted outright, rather than left as unused dead code. `Workspaces.qml`/`Tray.qml` (containers, not single clickable items) are intentionally still unmigrated.
- **`WidgetButton`'s content slot is a `Row` (`contentRow`), not a bare `Item`**: a content `Text` (or anything else passed as `WidgetButton`'s default-property content) must not set `anchors.centerIn`/`fill`/etc. on itself — `Row` logs "Cannot specify left, right, horizontalCenter, fill or centerIn anchors for items inside Row. Row will not function." and silently stops laying out. Hit refactoring `Button.qml`: its original `Text` (previously a direct child of `Button`'s own root `Rectangle`, pre-refactor) had `anchors.centerIn: parent`, which had to be dropped once it became `WidgetButton` content — a plain `Text` with no anchors lays out fine via `contentRow`'s own `anchors.centerIn: parent` and `Row` spacing.
- **`UpdatesIndicator`'s "up to date" look ported onto `idle`, not a raw `color:` override**: the original `Pill`-based widget overrode `color` directly (`hovered ? hoverBackground : (count > 0 ? background : transparent)`). Migrated onto `WidgetButton`'s `idle` flag instead (`idle: Updates.count === 0`, `styleOverrides: root.resolveStyle({ idleBackground: "transparent" })`), since "nothing pending" reading as dimmed/transparent is exactly what `idle` models — precedence (`hovered` still wins over `idle`) matched the original ternary's ordering without needing a hand-written override. `IdleInhibitorIndicator`'s toggled-"on" lavender stayed a direct `color:` override instead, since a committed/attention-getting state is the opposite of what `idle`/`inactive`'s current default colors model — forcing every state-driven color through `idle`/`inactive` isn't the goal, using whichever fits is.
- **`WidgetButton`'s `style` input must be merged with its own defaults, not just assigned**: `resolvedBackground`/`resolvedTextColor` are `readonly property color` *bindings*, which QML evaluates eagerly on creation and on every dependency change — regardless of whether anything ever reads them. Refactoring `NotificationsIndicator.qml` (which never reads `resolvedTextColor`, it colors its own `Text` with a literal `Colors.text`) still passed a `style` object missing `textColor`/`hoverTextColor` — `resolvedTextColor`'s fallback branch read `root.style.textColor` as `undefined`, and `Colors.resolve(undefined)` returns `undefined` too, producing a real QML warning ("Could not find any constructor for value type QQuickColorValueType to call with value undefined" / "Unable to assign [undefined] to QColor") every time, purely from an unused property. Fixed by having `WidgetButton` itself merge whatever partial object is passed (now named `styleOverrides`) over an internal `defaultStyle` (`Object.assign({}, defaultStyle, styleOverrides)`) into the `style` property everything (internal bindings and the composing widget alike) actually reads — a composing widget's `styleOverrides` can safely specify only the keys it cares about, same spirit as `Settings.widgetStyle`'s JSON-over-defaults merge, just one layer earlier.
